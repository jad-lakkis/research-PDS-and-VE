Updated after every future decision, not just retroactively.

Status legend: **Confirmed** = settled, acted on. **Provisional** = in place but explicitly flagged as needing revisit (e.g. once real data/professor input exists). **Open** = not yet decided.

## Mechanics verified against installed package source (not assumed)

Five separate verification passes this project, each reading `stable_baselines3==2.9.0`/`gymnasium==1.3.0` source directly rather than relying on general knowledge. Headline findings, since these constrain future design choices too:

1. `PPO()` only auto-wraps a raw env in `Monitor`+`DummyVecEnv` when it's *not already* a `VecEnv` — `VecNormalize` is itself a `VecEnv`, so once it's used the whole stack (`Monitor`, `DummyVecEnv`) must be built by hand.
2. `env_method`/`get_attr`/`set_attr` pass straight through `VecNormalize` to the wrapped `DummyVecEnv` unchanged — safe to add `VecNormalize` without touching any existing `env_method`-based callback logic.
3. `EventCallback`/`EveryNTimesteps` **never forwards `on_rollout_end`** to a wrapped child callback — any callback needing `_on_rollout_end` must be a top-level entry in `callbacks=[...]`, not nested.
4. SB3's `VecEnv.reset()` has no per-call `seed=`/`options=` support in this version (unlike gymnasium's `Env.reset()`) — driving specific (trace, seed) pairs through a `VecEnv` isn't straightforward, and touching the *training* env's Vec stack out-of-band from a callback would desync `OnPolicyAlgorithm`'s cached `_last_obs`. `VecNormalize.normalize_obs()` is a safe, stateless, read-only alternative for applying learned normalization to a standalone (non-Vec) env's observations.
5. `EvalCallback`'s own auto-wrap doesn't understand `VecNormalize` — passing a bare eval env would crash with an uncaught `AssertionError` on the first evaluation call, well after training had already run cleanly. (This, combined with #3 and #4, is why evaluation ended up as a fully custom callback rather than SB3's stock `EvalCallback`.)
